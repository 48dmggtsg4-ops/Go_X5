# Сервис заказов

Учебный backend-сервис на Go. Позволяет создавать заказы, получать
заказ и список заказов, изменять статус и просматривать историю статусов.

Данные хранятся в памяти и удаляются после остановки приложения.

## Технологии

- Go 1.22+
- chi — HTTP-маршрутизация
- log/slog — структурированные JSON-логи
- Swaggo и Swagger UI — документация API
- testing и testify/require — модульные тесты

## Запуск

Все команды выполняются из папки с go.mod:

```bash
go mod download
go run ./cmd/api
```

По умолчанию сервер слушает порт 8080.

Для изменения адреса:

```bash
HTTP_ADDR=:9090 go run ./cmd/api
```

## API

Запросы и ответы используют JSON.

| Метод | Путь | Назначение | Успешный код |
|---|---|---|---|
| GET | /health | Проверка доступности | 200 |
| POST | /api/v1/orders | Создание заказа | 201 |
| GET | /api/v1/orders | Список заказов | 200 |
| GET | /api/v1/orders/{id} | Получение заказа | 200 |
| PATCH | /api/v1/orders/{id}/status | Изменение статуса | 200 |
| GET | /api/v1/orders/{id}/history | История статусов | 200 |

### Создание заказа

```bash
curl -i -X POST http://localhost:8080/api/v1/orders \
  -H 'Content-Type: application/json' \
  -d '{"items":[{"name":"Keyboard","quantity":2,"price":500000}]}'
```

Заказ должен содержать хотя бы одну позицию. Название товара
не должно быть пустым или состоять только из пробелов.
Количество и цена должны быть положительными.

Цена хранится целым числом в копейках.
Итоговая стоимость рассчитывается как сумма price × quantity.
Переполнение итоговой стоимости отклоняется.

### Статусы

Новый заказ получает статус new.

Разрешённые переходы:

- new → processing
- new → cancelled
- processing → completed
- processing → cancelled

completed и cancelled — конечные статусы.
Повторная установка текущего статуса запрещена.

При создании заказа и каждом успешном изменении статуса
добавляется запись истории со временем события.

Пример изменения статуса:

```bash
curl -i -X PATCH http://localhost:8080/api/v1/orders/1/status \
  -H 'Content-Type: application/json' \
  -d '{"status":"processing"}'
```

### Ошибки

Единый формат:

```json
{
  "error": "order not found",
  "code": "ORDER_NOT_FOUND"
}
```

- 400 — некорректный JSON, ID, данные заказа или неизвестный статус.
- 404 — заказ не найден.
- 409 — недопустимый переход статуса.
- 500 — внутренняя ошибка.

Внутренние подробности ошибок не возвращаются клиенту.

## Архитектура

- cmd/api — запуск сервера и сборка зависимостей.
- internal/order — предметные типы, ошибки и интерфейс репозитория.
- internal/repository/memory — хранилище в памяти.
- internal/service — валидация и бизнес-правила.
- internal/handler — HTTP-маршруты, обработчики и middleware.
- docs — сгенерированная Swagger-документация.

Зависимости передаются через конструкторы.
Сервис работает с интерфейсом репозитория.

Хранилище защищено sync.RWMutex и возвращает копии срезов
позиций и истории.

## Логирование

Каждый HTTP-запрос записывается в JSON-лог с полями:

- method
- path
- status
- duration
- request_id

Идентификатор запроса также возвращается в заголовке X-Request-ID.

Recovery middleware перехватывает панику и записывает её в лог.
Если ответ ещё не начат, клиент получает безопасный JSON с кодом 500.

## Swagger

После запуска приложения:

http://localhost:8080/swagger/index.html

Повторная генерация после изменения аннотаций:

```bash
go run github.com/swaggo/swag/cmd/swag@v1.16.4 init -g cmd/api/main.go -o docs --parseInternal
```

Сгенерированные docs.go, swagger.json и swagger.yaml
должны находиться в Git-репозитории.

## Проверки

```bash
go test ./...
go test ./internal/service -cover
go vet ./...
go build ./...
```

Тесты сервиса используют подставной репозиторий и table-driven подход.
Они проверяют создание и валидацию заказа, расчёт стоимости,
получение заказов, переходы статусов, историю и ошибки хранилища.

Требуемое покрытие пакета service — не менее 80%. (покрытие - 100%)
